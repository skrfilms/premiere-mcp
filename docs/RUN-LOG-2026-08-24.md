### Sentinel bugs found and fixed while validating it

Recorded because each one would have made the sentinel *lie*, and a lying sentinel is worse
than none — it is the component every other honesty claim rests on:

1. **Unwrapped `return`.** The probe sent `return JSON.stringify(...)` raw; a top-level `return`
   is a syntax error in `evalScript`, and the panel reports it with the same generic
   `EvalScript error.` string it uses for a genuinely dead host. The probe would have accused a
   healthy engine of being dead. Now wrapped in an IIFE, matching `src/bridge/index.ts:637`.
2. **`result` is already parsed.** `JSON.parse(payload.result)` threw because the panel had
   already decoded it to an object. Verdict was `ENGINE_DEAD` against a host that had answered
   correctly in 103 ms. Now accepts object *or* string.
3. **Wrong env var name.** Used `PREMIERE_MCP_TEMP_DIR`; the name the server and panel agree on
   is `PREMIERE_TEMP_DIR`. Accepts both now, prefers the real one.

Worth stating plainly: the sentinel returned two false `ENGINE_DEAD` verdicts before it
returned a true `HEALTHY` one. It reported them honestly enough to be debuggable, but "the
component that detects lying" needed three fixes before it stopped lying, and it should get a
unit test against recorded payloads rather than only ever being validated against a live host.

### 01:30–02:00 — the time-representation bug class. Nine tools were silently inert.

Chased the `undefined` and measured the actual shapes on 26.3.2:

| accessor | type | unit |
|---|---|---|
| `Sequence.end` | **string** | **TICKS** |
| `Sequence.getInPoint()` / `getOutPoint()` | **string** | **SECONDS** |
| `ProjectItem.getInPoint()` / `getOutPoint()` | Time object | `.ticks` / `.seconds` |
| `TrackItem.start` / `end` / `inPoint` / `outPoint` | Time object | `.ticks` / `.seconds` |

The two Sequence accessors have the **same type and different units** with nothing in the value
to distinguish them. Reading `.ticks` off either gives `undefined`, which becomes the literal
string `"undefined"` at `setPlayerPosition` (playhead silently does not move) or `NaN` in a
duration sum (serialised as `null`).

Nine call sites were wrong, and **most reported `success: true` — three with `verified: true` —
because they never compared a readback**: `go_to_sequence_end`, `go_to_in_point`,
`go_to_out_point`, `step_frames`, `clear_work_area`, `get_sequence_duration`,
`get_project_stats`, `validate_project_for_export`, `assemble_reel` (its cursor advanced by
`NaN`, so every source stacked at position 0).

Fixed with explicit **per-accessor** prelude helpers, deliberately not one unit-sniffing
function — a magnitude heuristic cannot tell 2 seconds from 2 ticks, and a wrong guess is
undetectable. Plus `__setPlayheadVerified`, which refuses a non-numeric target outright and
proves the move by readback.

Live-verified after the fix: `go_to_sequence_end` → 10s, `go_to_out_point` → 3s, `step_frames`
+10/−4 exact, `get_sequence_duration` → 10s/240 frames, `get_project_stats` → 20s.

**Two further measurements worth keeping:**

- **`setInPoint`/`setOutPoint` units depend on ARGUMENT TYPE**: a *number* is seconds, a *string*
  is ticks. `setInPoint('1.5')` sets 1.5 **ticks** ≈ 0 and reads back `0`. So passing a
  stringified seconds value silently zeroes the point. `__secondsToTicks()` returns a string and
  is therefore correct; `JSON.stringify(seconds)` is not.
- **The work-area setters are INERT on 26.3.2.** `setWorkAreaInPoint`/`setWorkAreaOutPoint` exist
  and throw nothing, QE `setWorkInOutPoints` likewise, and the readback never moves — even after
  `setWorkAreaEnabled(true)` flips `isWorkAreaEnabled()` from false to true. Premiere 2026
  deprecated the work-area bar in favour of sequence in/out points. `set_work_area` now says
  exactly that and points at the tool that works, instead of reporting a bare mismatch and
  inviting a retry that cannot succeed. Separately, `clear_work_area` had been calling
  `setWorkInPoint` — a **QE-only** name — on the DOM object.

**A verification lesson I had to apply to my own fix.** `clear_work_area` initially "verified"
successfully because its target (0 → sequence end) already equalled the current value. A no-op
and a real change read back identically whenever the target matches the existing state — which
is how a tool that does nothing passes its own check. It now reports `changed` and
`alreadyFullSequence` separately.

**Ergonomics fix found along the way:** `sequenceId` was *required* on 30 tools while 193 already
defaulted to the active sequence. An agent calling `get_playhead_position` had to go look up a
sequence ID first. Made optional on 28; kept required on `delete_sequence` (destructive) and
`set_active_sequence` (the id is the entire payload). `__findSequence` now falls back to the
active sequence rather than returning "Sequence not found".

**Test-infrastructure debt paid:**
- `undefined-identifiers` mirrored the prelude's helper names **by hand**, so adding a helper
  broke the suite with a message pointing at the tool that used it, and the obvious fix was to
  maintain the duplicate. Now **derived** from `EXTENDSCRIPT_HELPERS` by regex, so a helper is
  known the moment it exists and stops being known when deleted.
- `injection-guard` gained a per-**position** exemption. `batch_execute.operations[].script` is
  concatenated verbatim by contract, but the only lever available was a whole-tool skip that
  would also have stopped fuzzing its sibling `id`, which genuinely must be escaped.

### 02:00–02:20 — ADOBE SHIPS A NATIVE MCP SERVER. Verified first-hand.

A survey agent reported this; it was consequential enough that I verified it independently
rather than relaying it. **It is real.** Full write-up with evidence and method in
**`docs/ADOBE-NATIVE-MCP.md`** — that document is the important artifact of the night.

Premiere Pro 2026 (26.3.2, installed here) contains **Preferences ▸ Agents ▸ "Model Context
Protocol Server"**, endpoint `http://localhost:3000/premiere/mcp`, configurable port, "Require
Authentication" with a generated token, and a "Copy MCP Configuration" button. In the binary:
`dvamcp::MCPServer` and the literal string **"Rust MCP server"**, `IMCPToolHandler` /
`IMCPPromptHandler` / `IMCPResourceHandler`, prompt + resource + **resource-template**
registration, the complete MCP content model (Text/Image/Audio/EmbeddedResource/ResourceLink),
and **both input and output schema validation**. ~30 tools, all primitives. Plus
`UXPMCPHandler` (third-party UXP plugins can register tools **into** Adobe's server) and
`MCPScriptingExtensibilityAPIObject` exposing `CallMCPTool` / `ListMCPTools`.

**Method note worth remembering:** `strings` and `grep -a` both time out on the 724 MB binary
because it has essentially no newlines. My first two scans returned nothing and I nearly
recorded a false negative on tooling grounds. `mmap` + regex in Python returns in seconds.

**Tested:** our CEP/ExtendScript bridge **cannot** reach `CallMCPTool` as shipped — `typeof MCP`
is `undefined`, nothing on `app`, nothing in `$.global`. Consistent with the binary's own
wording that `callMCPTool` is *"pre-injected"* per execution, i.e. it belongs to the engine
`executeMCPScript` runs in, not the legacy engine CEP talks to.

**DECISION (2, logged): I did not enable Adobe's MCP server.** It opens a persistent network
listener and changes the owner's application configuration. That is the owner's call, it is not
required for anything else tonight, and the strategic finding is established without it. The
open question it would settle — whether enabling registers the scripting object into the
ExtendScript context, which would let our bridge call Adobe's native tools with no new transport
— is written up with a 2-minute repro in `ADOBE-NATIVE-MCP.md` §4.

Strategic read, in one line: **Adobe owns the primitives; do not compete there.** Their ~30 tools
touch none of export/encode, render-truth, Lumetri, audio, captions, proxies, MOGRT, keyframe
interpolation, the QE-only capabilities, Project Manager, EDL/AAF/OMF/FCPXML, multicam,
stabilisation, or verification. Schema validation is argument checking, not proof an edit landed,
so the honesty layer is worth *more* now, not less. And `RegisterUXPMCPHandler` is plausibly the
distribution answer rather than a threat.
