### Sentinel bugs found and fixed while validating it

Recorded because each one would have made the sentinel *lie*, and a lying sentinel is worse
than none — it is the component every other honesty claim rests on:

1. **Unwrapped `return`.** The probe sent `return JSON.stringify(...)` raw; a top-level `return`
   is a syntax error in `evalScript`, and the panel reports it with the same generic
   `EvalScript error.` string it uses for a genuinely dead host. The probe would have accused a
   healthy engine of being dead. Now wrapped in an IIFE, matching `src/bridge/index.ts:637`.
2. **`result` is already parsed.** `JSON.parse(payload.result)` threw because the panel had
   already decoded it to an object. Verdict was `ENGINE_DEAD` against a host that had answered
   correctly in 103 ms. Now accepts object *or* string.
3. **Wrong env var name.** Used `PREMIERE_MCP_TEMP_DIR`; the name the server and panel agree on
   is `PREMIERE_TEMP_DIR`. Accepts both now, prefers the real one.

Worth stating plainly: the sentinel returned two false `ENGINE_DEAD` verdicts before it
returned a true `HEALTHY` one. It reported them honestly enough to be debuggable, but "the
component that detects lying" needed three fixes before it stopped lying, and it should get a
unit test against recorded payloads rather than only ever being validated against a live host.

### 01:30–02:00 — the time-representation bug class. Nine tools were silently inert.

Chased the `undefined` and measured the actual shapes on 26.3.2:

| accessor | type | unit |
|---|---|---|
| `Sequence.end` | **string** | **TICKS** |
| `Sequence.getInPoint()` / `getOutPoint()` | **string** | **SECONDS** |
| `ProjectItem.getInPoint()` / `getOutPoint()` | Time object | `.ticks` / `.seconds` |
| `TrackItem.start` / `end` / `inPoint` / `outPoint` | Time object | `.ticks` / `.seconds` |

The two Sequence accessors have the **same type and different units** with nothing in the value
to distinguish them. Reading `.ticks` off either gives `undefined`, which becomes the literal
string `"undefined"` at `setPlayerPosition` (playhead silently does not move) or `NaN` in a
duration sum (serialised as `null`).

Nine call sites were wrong, and **most reported `success: true` — three with `verified: true` —
because they never compared a readback**: `go_to_sequence_end`, `go_to_in_point`,
`go_to_out_point`, `step_frames`, `clear_work_area`, `get_sequence_duration`,
`get_project_stats`, `validate_project_for_export`, `assemble_reel` (its cursor advanced by
`NaN`, so every source stacked at position 0).

Fixed with explicit **per-accessor** prelude helpers, deliberately not one unit-sniffing
function — a magnitude heuristic cannot tell 2 seconds from 2 ticks, and a wrong guess is
undetectable. Plus `__setPlayheadVerified`, which refuses a non-numeric target outright and
proves the move by readback.

Live-verified after the fix: `go_to_sequence_end` → 10s, `go_to_out_point` → 3s, `step_frames`
+10/−4 exact, `get_sequence_duration` → 10s/240 frames, `get_project_stats` → 20s.

**Two further measurements worth keeping:**

- **`setInPoint`/`setOutPoint` units depend on ARGUMENT TYPE**: a *number* is seconds, a *string*
  is ticks. `setInPoint('1.5')` sets 1.5 **ticks** ≈ 0 and reads back `0`. So passing a
  stringified seconds value silently zeroes the point. `__secondsToTicks()` returns a string and
  is therefore correct; `JSON.stringify(seconds)` is not.
- **The work-area setters are INERT on 26.3.2.** `setWorkAreaInPoint`/`setWorkAreaOutPoint` exist
  and throw nothing, QE `setWorkInOutPoints` likewise, and the readback never moves — even after
  `setWorkAreaEnabled(true)` flips `isWorkAreaEnabled()` from false to true. Premiere 2026
  deprecated the work-area bar in favour of sequence in/out points. `set_work_area` now says
  exactly that and points at the tool that works, instead of reporting a bare mismatch and
  inviting a retry that cannot succeed. Separately, `clear_work_area` had been calling
  `setWorkInPoint` — a **QE-only** name — on the DOM object.

**A verification lesson I had to apply to my own fix.** `clear_work_area` initially "verified"
successfully because its target (0 → sequence end) already equalled the current value. A no-op
and a real change read back identically whenever the target matches the existing state — which
is how a tool that does nothing passes its own check. It now reports `changed` and
`alreadyFullSequence` separately.

**Ergonomics fix found along the way:** `sequenceId` was *required* on 30 tools while 193 already
defaulted to the active sequence. An agent calling `get_playhead_position` had to go look up a
sequence ID first. Made optional on 28; kept required on `delete_sequence` (destructive) and
`set_active_sequence` (the id is the entire payload). `__findSequence` now falls back to the
active sequence rather than returning "Sequence not found".

**Test-infrastructure debt paid:**
- `undefined-identifiers` mirrored the prelude's helper names **by hand**, so adding a helper
  broke the suite with a message pointing at the tool that used it, and the obvious fix was to
  maintain the duplicate. Now **derived** from `EXTENDSCRIPT_HELPERS` by regex, so a helper is
  known the moment it exists and stops being known when deleted.
- `injection-guard` gained a per-**position** exemption. `batch_execute.operations[].script` is
  concatenated verbatim by contract, but the only lever available was a whole-tool skip that
  would also have stopped fuzzing its sibling `id`, which genuinely must be escaped.

855 tests green. Committed as `b5e75c8`.

### 02:00–02:20 — ADOBE SHIPS A NATIVE MCP SERVER. Verified first-hand.

A survey agent reported this; it was consequential enough that I verified it independently
rather than relaying it. **It is real.** Full write-up with evidence and method in
**`docs/ADOBE-NATIVE-MCP.md`** — that document is the important artifact of the night.

Premiere Pro 2026 (26.3.2, installed here) contains **Preferences ▸ Agents ▸ "Model Context
Protocol Server"**, endpoint `http://localhost:3000/premiere/mcp`, configurable port, "Require
Authentication" with a generated token, and a "Copy MCP Configuration" button. In the binary:
`dvamcp::MCPServer` and the literal string **"Rust MCP server"**, `IMCPToolHandler` /
`IMCPPromptHandler` / `IMCPResourceHandler`, prompt + resource + **resource-template**
registration, the complete MCP content model (Text/Image/Audio/EmbeddedResource/ResourceLink),
and **both input and output schema validation**. ~30 tools, all primitives. Plus
`UXPMCPHandler` (third-party UXP plugins can register tools **into** Adobe's server) and
`MCPScriptingExtensibilityAPIObject` exposing `CallMCPTool` / `ListMCPTools`.

**Method note worth remembering:** `strings` and `grep -a` both time out on the 724 MB binary
because it has essentially no newlines. My first two scans returned nothing and I nearly
recorded a false negative on tooling grounds. `mmap` + regex in Python returns in seconds.

**Tested:** our CEP/ExtendScript bridge **cannot** reach `CallMCPTool` as shipped — `typeof MCP`
is `undefined`, nothing on `app`, nothing in `$.global`. Consistent with the binary's own
wording that `callMCPTool` is *"pre-injected"* per execution, i.e. it belongs to the engine
`executeMCPScript` runs in, not the legacy engine CEP talks to.

**DECISION (2, logged): I did not enable Adobe's MCP server.** It opens a persistent network
listener and changes the owner's application configuration. That is the owner's call, it is not
required for anything else tonight, and the strategic finding is established without it. The
open question it would settle — whether enabling registers the scripting object into the
ExtendScript context, which would let our bridge call Adobe's native tools with no new transport
— is written up with a 2-minute repro in `ADOBE-NATIVE-MCP.md` §4.

Strategic read, in one line: **Adobe owns the primitives; do not compete there.** Their ~30 tools
touch none of export/encode, render-truth, Lumetri, audio, captions, proxies, MOGRT, keyframe
interpolation, the QE-only capabilities, Project Manager, EDL/AAF/OMF/FCPXML, multicam,
stabilisation, or verification. Schema validation is argument checking, not proof an edit landed,
so the honesty layer is worth *more* now, not less. And `RegisterUXPMCPHandler` is plausibly the
distribution answer rather than a threat.

### 02:20–02:45 — auto-recovery built and PROVEN, and the default profile flipped

**Auto-recovery works: 32 seconds, end to end.** `scripts/lib/host-recovery.mjs`. Quit → relaunch
with the project → panel autostarts → engine verified → fixture rebuilt. Engine death stopped being
fatal to a run. Two things had to be fixed before it worked:

- The first attempt reported *"Premiere would not exit even after SIGKILL"*. It had exited:
  **Adobe's crash reporter reads the dying process's memory and parks the corpse in
  uninterruptible-exiting state (`ps` STAT `UE`)**, where SIGKILL looks like a no-op and `pgrep`
  keeps listing an already-departing PID. An `AdobeCrashReport -p <pid>` process was holding it;
  killing the reporter freed it instantly. Recovery now reaps the reporters and treats `E`/`Z` as
  gone.
- SIGTERM on an unsaved scratch project raises **"Save changes?"**, which blocks the quit forever
  and pushes you into the SIGKILL path above. So: if the engine still answers, `app.project.save()`
  first, *then* SIGTERM. Saving is not about the contents; it is about leaving Premiere no question
  to ask.

**DECISION (3, logged): flipped the default tool profile from `all` to `core`.** Measured:
638 tools ≈ 102,000 tokens ≈ **51% of a 200k context window** spent before the user says anything.
Anthropic's guidance puts selection degradation past ~30–50 tools; MCP's client best-practice doc
suggests deferring past 1–5%; and **VS Code / Copilot hard-errors above 128**, so the old default
could not run there at all. `all` is one env var away.

Curation is only honest because `find_tool` searches all 638 and reports a hidden match as
`exposed: false` **with the reason**. Verified live under the new default: "normalize loudness" and
"export aaf" return the real tool names flagged hidden, with a note on how to widen. Without that,
a curated build is indistinguishable from one where the feature was never written.

`core` grew 64 → 97 because 64 was **incoherent**: `apply_effect` shipped without
`set_effect_property` (add Gaussian Blur, no way to set its blurriness), `bake_keyframe_ease`
without `add_keyframe`, and **no `undo`/`redo` at all**. A default that forces a profile switch on
the second call is not a default.

**The owner's `.mcp.json` now pins `PREMIERE_MCP_PROFILE=all`,** so their setup is unchanged. That
was deliberate: waking up to 570 missing tools mid-edit is not an acceptable way to learn about a
default change.

Also fixed: `api_surface_report` published a hardcoded `total_tools: 600` against a 638-tool build
and still listed the system clipboard as impossible after we cracked it. Counts are computed now,
wall entries carry their evidence, and a `cracked_since` field records removals. **A stale "cannot
do" list is the same class of lie as a fake success** — it tells an agent to stop trying something
that works.

### Real bugs found by executing, and fixed

None of these were reachable by any static check, and two were failing **silently**:

- **`grade_snapshot`** called `n.trim()` and `n.startsWith('_')` → `ReferenceError` on every call.
  It could never return a grade.
- **`clear_sequence_in_out`** called `seq.clearInPoint(0)` / `clearOutPoint(0)`. Those are
  **ProjectItem** methods and are **undefined on Sequence** — it threw every time. There is no true
  "clear" for a sequence range (an unset range reads back as 0 → end), so it now resets to the full
  sequence, verifies both points, and says that a reset is the honest equivalent. Verified: 1s→3s
  became 0s→12s.
- **`export_thumbnail`** returned `success: false` with **no error field at all**, just
  `qeResult: "false"`. Its file-exists check was already correct; the failure was mute. QE frame
  export is inert on this build, so it now falls back to **ffmpeg** against the source media under
  the playhead — and reports the difference rather than smoothing it: the fallback is the SOURCE
  frame, no effects, no transitions, nothing from higher tracks, and it names
  `capture_program_output` for a composited frame. Verified: a real 158K PNG at 00:00:02:00.

**And the ES3 rule of thumb turned out to be wrong in both directions.** Measured live:

| | |
|---|---|
| **PRESENT** | `Array.prototype.map`, `filter`, **`indexOf`** |
| **ABSENT** | `Array.prototype.forEach`, `String.prototype.trim`, `startsWith`, `endsWith`, `includes`, `Object.keys` |

Both halves mattered. I had 13 `.map`/`.filter` call sites queued for a rewrite on the assumption
they were ES5-only — measuring first saved all of them. Meanwhile `trim` really was absent. This
also **corrects a memory note** that claimed `indexOf` was unavailable.

New suite `es3-absent-methods.test.ts` drives every registered tool, captures the script actually
**sent to the host**, and fails on any call to a measured-absent built-in. It checks only host
script text, because a hand audit of the source could not distinguish host script from Node-side
TypeScript and produced false positives on both `Object.keys` and `.map`. Its positive control
targets the **detector**, not the seeding: the patterns must fire on known-bad text and stay silent
on the ES3-safe replacements, so a regex that quietly stopped matching cannot let the suite pass
vacuously.

### 04:20–05:40 — a second pass of real bugs, including one I introduced

The final sweeps confirmed the engine-killer fix (**0 engine kills**, down from 1) and surfaced
another batch of genuine defects. The pattern in all of them is the same: they reported something
other than what had actually happened.

- **Both proxy tools were structurally unable to report the truth.** `app.getEnableProxies()`
  returns a **number** (1/0), not a boolean. `get_proxies_enabled` compared `enabled === true`, so
  it **could only ever answer "OFF"** — including when proxy playback was on. This is the tool that
  answered the owner's proxy question yesterday: the conclusion I drew from it was correct and they
  confirmed it, but **the tool could not have told me otherwise.** `set_proxies_enabled` had the
  mirror bug and reported failure on a write that succeeded. Both now compare truthiness, expose the
  raw value, and say plainly that this is the GLOBAL toggle and a clip still needs an attached proxy.
  Verified: read true (raw 1) → set OFF → `changed: true` → read false (raw 0).
- **`enable_disable_effect` was verifying its own write.** It set `component.enabled` and — in *my*
  first fix — read it back. `VideoComponent` has **no `enabled` property**; `typeof` is `undefined`
  on every component. The assignment created a stray JS property on the ScriptObject, so the
  readback confirmed my write and said nothing about Premiere. **A verification that cannot fail is
  worse than none.** The real toggle is the component's own **"Active" parameter**, which I
  round-tripped before relying on it (true → false → true). Now: Lumetri toggles for real; Motion,
  which exposes no Active param, is refused with an explanation.
- **`remove_mogrt_clip`** called `seq.remove(...)`. `Sequence` has no `remove()` — it is on
  `TrackItem`. Every call raised a ReferenceError, and the dead-end fallback beneath it built two
  `Time` objects and did nothing with them, so the tool returned `success: true, verified: false`.
- **`batch_replace_clips`** called `clip.replaceWithClip()`, which does not exist. There is no DOM
  replace at all, so it is now remove + `overwriteClip` at the same start time — with targets
  collected **before** mutating, because removing a clip reshuffles `track.clips` indices and the
  original would have skipped clips even if the method had existed. Verified: 2 replaced, 0 failures.
- **`duplicate_clip`** verified by track **count**, but `overwriteClip` *overwrites*: dropped on
  occupied time it replaces rather than appends, so an unchanged count is correct and the tool
  reported a false negative on a duplicate that had landed. It now looks for a clip referencing the
  same source at the target time and reports `replacedExisting`.
- **An unset sequence in/out range reports a NEGATIVE seconds value** (about one frame below zero),
  not null — so `go_to_in_point`/`go_to_out_point` tried to move the playhead to a negative tick
  position and failed with an accurate but useless "did not land" message. Negative is now treated
  as "not set", and the tools name `set_sequence_in_out_points`.

**And one I introduced and our own suite caught:** the `sequence_from_markers` rewrite interpolated
`markerType` **raw** into a single-quoted ExtendScript string, so a quote in the value broke out of
the literal. The injection-guard suite flagged it two commits later. Fixed and re-verified with a
hostile value. That suite takes nine minutes to run and it earned every one of them tonight.

Ten rules were distilled from all of this into `docs/TROWEL-PLAN.md` §6.5, because most of them are
general and would otherwise be re-learned.

# THE MORNING REPORT

Read this bit. Everything above is the evidence.

## The one thing that matters most

**Adobe ships its own MCP server inside Premiere Pro 2026.** `Preferences ▸ Agents`,
`http://localhost:3000/premiere/mcp`, token auth, a Rust server, prompts + resources + resource
templates, input *and* output schema validation, ~30 tools. Off by default. Adobe has published
nothing about it; I read it out of the application bundle and verified it twice.
**`docs/ADOBE-NATIVE-MCP.md`** is the write-up and is the most important artifact of the night.

It does not make Trowel pointless — it tells us what Trowel is. Adobe shipped the **primitives**
(project/bin/sequence/track/clip CRUD, effect params, markers, labels, transcript, search). Their
surface touches **none** of export/encode, render-truth, Lumetri, audio, captions, proxies, MOGRT,
keyframe interpolation, the QE-only capabilities, Project Manager, EDL/AAF/OMF/FCPXML, multicam,
stabilisation, or verification. And their schema validation checks *arguments*, not whether an edit
landed — so the honesty layer is worth **more** now, not less.

Two consequences I'd want you to weigh:
1. **Stop treating our transport as the moat.** A first-party server will out-reliable a CEP
   file-IPC bridge eventually. I have flagged the WebSocket work as a maintenance question, not a
   strategic one.
2. **`RegisterUXPMCPHandler` may be the distribution answer.** Third-party UXP plugins can register
   tools *into* Adobe's server, inheriting their transport, auth and validation — letting us delete
   the most fragile thing we own. "Register into it" plausibly beats "compete with it."

**One decision waiting for you:** enabling their server opens a persistent network listener on your
machine, so I did not do it. Doing so would settle the highest-value open question — whether it
registers a scripting object our existing bridge could call Adobe's native tools through, with no
new transport. Two-minute repro in `ADOBE-NATIVE-MCP.md` §4.

## What got better, with numbers

- **Live coverage 231 → 441 tools (38% → 69%).** The sweep is now reason-typed: 47 tools remain
  untested and each says why (20 slow/AME, 7 modal, 5 host-state, 4 arbitrary, 4 cloud, 4 outside,
  3 playback). No more single opaque "~95 unsafe".
- **Engine death stopped being fatal.** `engine-sentinel.mjs` tells a dead engine from a dead panel
  from a busy one; `host-recovery.mjs` quits, relaunches, clears modals, verifies and rebuilds the
  fixture in **~32 seconds**. It fired for real mid-sweep on `sequence_from_markers` and the run
  continued. This was Tier 0a #1, described in the plan as "the most important thing in this
  document".
- **We can clear a native modal unattended.** Premiere exposes zero windows to the accessibility
  API, so clicking a dialog button is impossible — but System Events **keystrokes** reach the
  frontmost app, and Escape dismisses Link Media and the New Sequence dialog. That turns a 32-second
  restart into a **6-second** recovery, and it is most of Tier 0 #2.
- **Tests: 5 failing → 0.** 858 passing. Two new suites, and both earned it: the ES3 guard found a
  whole class, and the injection guard caught a hole *I* introduced.
- **Build was RED at handover.** Fixed in the first ten minutes.

## The bugs worth telling you about

All found by *executing* tools. None were reachable by static analysis, and most reported success:

- **Nine tools were silently inert** because `Sequence.end` is a ticks **string** while
  `Sequence.getInPoint()` is a seconds **string** — same type, different units, nothing in the value
  to tell them apart. `go_to_sequence_end`, `go_to_in_point`, `go_to_out_point` were passing the
  literal text `"undefined"` to `setPlayerPosition` and **reporting `verified: true`**.
  `get_project_stats` was summing `NaN` and shipping `null`.
- **`createNewSequence` opens the New Sequence dialog.** That was the engine-killer: 45-second
  timeout, panel stops polling, indistinguishable from a dead engine. Three tools used it. My first
  hypothesis (duplicate sequence ids) was wrong and I only found the real cause because a comment
  in our own bridge already said `newSequence` is the non-interactive API. `sequence_from_markers`
  is now rewritten on `createSubsequence` and actually does what it always claimed.
- **`grade_snapshot`** called `.trim()` and `.startsWith()` — neither exists in this engine — so it
  threw on every call and could never return a grade.
- **`clear_sequence_in_out`** called ProjectItem methods on a Sequence; threw every time.
- **`export_thumbnail`** returned `success: false` with **no error field at all**. It now falls back
  to ffmpeg and produces a real frame, labelled honestly as a *source* frame rather than a
  composited one.
- **`work area` writes are inert on 26.3.2** — accepted, never applied, even after enabling it.
  `set_work_area` now says so and names the tool that works instead of inviting a retry.

## Things I got wrong, and one I nearly shipped

- **I introduced a script-injection bug** in `sequence_from_markers` by interpolating `markerType`
  raw into an ExtendScript string literal. Our own injection-guard suite caught it two commits
  later. Fixed and verified with a hostile value.
- **I nearly "fixed" 13 working call sites.** I assumed `Array.prototype.map`/`filter` were absent
  because "ExtendScript is ES3". Measuring first showed `map`, `filter` and `indexOf` are all
  **present**, while `forEach`, `trim`, `startsWith` and `Object.keys` are not. The rule of thumb
  was wrong in both directions. This also **corrects a memory note** that claimed `indexOf` was
  unavailable.
- **My own verification had the flaw it exists to catch.** `clear_work_area` "verified"
  successfully because its target already equalled the current value — a no-op and a real change
  read back identically. Every verify-after-write now has to capture `before` and report `changed`
  separately.
- **My sentinel returned two false `ENGINE_DEAD` verdicts** before it returned a true `HEALTHY`
  one. The component that detects lying needed three fixes before it stopped lying.
- **45 tools looked broken and were one broken harness** — I passed `ProjectItem.nodeId` where
  `TrackItem.nodeId` was wanted.
